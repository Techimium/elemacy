# Elementor compatibility surface — first-release baseline

Recorded against the installed Elementor **4.2.3**; the supported range, **3.35.9–4.2.3**, was confirmed from executable evidence against a second, independently provisioned Elementor 3.35.9 environment (see Known Limitations). This is an inventory of every Elementor API Elemacy's rendering, CSS, document, control and frontend-hydration code actually calls, not a claim that Elementor guarantees any of it will keep working. `F/` means the Elemacy plugin root; source paths without a prefix are relative to it. Pro's own Elementor surface is limited to the standard widget-authoring API already covered under "Controls" below (`Controls_Manager`, `Controls_Stack`, `Element_Base`, `Plugin`, `Widget_Base`) and is not repeated per-file.

## Classification

- **Public** — an entry point Elementor documents for third-party developers (a widget/control/document base class meant to be extended, or a hook listed on developers.elementor.com), or a WordPress-native mechanism Elementor participates in (shortcodes, filters). Expected to be stable across minor versions.
- **Internal** — reached only through a documented public entry point (`Plugin::instance->X`), but `X` itself (`Documents_Manager`, `Editor`, `Frontend`, `DB`) is one of Elementor's own service objects with no published method-level contract. Elementor is free to change these methods' internals between releases without notice.
- **Optional** — an entirely separate Elementor module/feature that may be absent depending on version or configuration (Atomic Widgets, Global Classes). Every optional entry below is guarded with `class_exists`/`function_exists` before use; per this task's own instruction, a passing guard is not itself evidence the guarded call still behaves as expected — each optional entry names the fixture that actually exercises it.

## Known limitations

- **RESOLVED: Atomic Widgets are exercised against genuinely atomic documents.** `tests/integration/atomic-rendering.php` authors styled `e-flexbox`, `e-heading` and `e-button` elements and drives them through Elementor's real traversal, style schema and `Styles_Renderer`: a Loop Item template emits its atomic base CSS once per template, and a style bound to a dynamic tag is emitted per rendered item, scoped to that item and carrying its own value (`fixtures/mu-plugins/atomic-dynamic-color-tag.php` supplies the color tag). An atomic Header delivers its atomic stylesheet on a real page rendered in a fresh process, and that test fails when `TemplateAssetsRegistrar` stops handing the document to `elementor/post/render`. `tests/integration/chrome-documents.php` covers atomic Header and Footer documents at the pipeline. Elementor only converts a classic dynamic tag for atomic use when every control carries a label, so Elemacy's own dynamic tags are not offered in atomic elements today; that is a feature gap, not a rendering one.
- **RESOLVED: `ClassicCssRenderer::has_dynamic_settings`'s use of `AtomicWidgets\Utils\Utils::traverse_post_elements` — named "accidental dependency" — no longer exists.** Reading that method's own implementation (`modules/atomic-widgets/utils/utils.php`) showed it was never Atomic-specific to begin with: it is exactly `Documents_Manager::get` + `Document::get_elements_data` + `DB::iterate_data`, three genuinely core Elementor calls, wrapped in the Atomic Widgets namespace. **New** `Elementor/Compatibility/ElementTreeWalker.php` calls those three core APIs directly, so classic dynamic-tag detection no longer depends on the Atomic Widgets module existing at all — verified by a fast-harness source-grep check that `ClassicCssRenderer.php` contains no reference to any Atomic Widgets class, and by real positive/negative traversal tests run against a classic-only stub with the Atomic Widgets classes never defined anywhere in that process.
- **`Widget_Icon_List`/`Widget_Image_Gallery`/`Widget_Accordion` extension is a materially more version-fragile surface than `Widget_Base` extension.** These three widgets rely on their parent's `register_controls`, `get_settings_for_display` and `render` internals continuing to accept the same settings shape and repeater/render-attribute helper methods across Elementor releases. No `class_exists` guard can catch a future signature change in these parents — only the real-render fixtures added by this task can, and they now do (see Controls table above). No prior fixture (integration, e2e, or fast-harness) exercised these three widgets at all before this task.
- **RESOLVED: supported Elementor range is 3.35.9–4.2.3, from executable evidence, not inference.** The full real-WordPress integration suite (225 scenarios), both real-browser suites (popup hydration and reopen; Loop Grid AJAX pagination hydration, including the second-consecutive-load regression case) and the complete fast harness were run against Elementor **3.35.9** (the last stable release before Elementor's 4.0 Atomic-widgets rewrite — downloaded from wordpress.org and provisioned as a second, independent disposable environment) and re-confirmed against the already-installed **4.2.3**, with identical results in both. `Core/CompatibilityChecker::MIN_ELEMENTOR_VERSION` (`3.35.9`) now enforces this floor at runtime (an admin notice plus automatic deactivation below it, mirroring the existing PHP-version check), and `elemacy.php`/`readme.txt` document it. Free builders were confirmed working with Elementor Pro genuinely absent from both environments (never installed, not merely inactive) in every one of these runs — the "Free builders work without Elementor Pro" claim asks to verify.
 - **A real, non-obvious finding surfaced by this exercise**: Elementor 3.35.9 already ships the Atomic Widgets/Global Classes *classes* this document's Section 2 (CSS) covers as "Optional" (`Modules\AtomicWidgets\Utils\Utils`, `Modules\GlobalClasses\Utils\Atomic_Elements_Utils`, `Modules\AtomicWidgets\Styles\Styles_Renderer`, `Modules\AtomicWidgets\DynamicTags\Dynamic_Prop_Type` all exist, confirmed via `class_exists` in that exact environment) — but the owning `atomic-widgets` experiment defaults to **inactive** there. Since PHP class autoloading is independent of Elementor's own experiment-activation state, `Capabilities::atomic_widgets` and friends report these as *present* in both 3.35.9 and 4.2.3 regardless of whether the feature is actually switched on — a `class_exists` guard proves the class loads, not that the experiment gating it is active. This doesn't change any documented behavior above (none of this project's fixtures author genuinely Atomic content in either version, so the guarded code paths correctly return empty/no-op identically either way — see the next bullet), but it sharpens exactly what "Optional" means for these four entries: optional in the sense of "may not exist depending on Elementor's build," not "may be dormant behind an experiment flag with no plugin-visible signal of that."
 - The Atomic-Widgets-content gap this exercise left open is closed: see the resolved Atomic Widgets entry above. `atomic-rendering.php` is part of the integration suite the CI matrix runs against both Elementor versions; it skips where the installed Elementor does not register atomic elements.
