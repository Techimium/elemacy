### Cache invalidation and rollout

The wire protocol itself is content-addressed, not time-based: `PublishedLoopDefinitionResolver` computes the fingerprint from the owner document's current `_elementor_data`, so *any* edit to the widget's saved settings (including its `template_id` or query options) changes the fingerprint on the very next read. A page cached before that edit still serves the old fingerprint in its markup; the first AJAX pagination request against it fails fingerprint comparison and returns the stable `elemacy_loop_refresh_required` error — never a fallback query against the stale settings, and never silently wrong data. No separate expiry/TTL exists for the fingerprint itself.

The signed host-context token (`PaginationContextSigner`) is independently reusable while its definition stays valid — it is deliberately not one-use — and needs no rollout-time invalidation of its own: it rotates automatically whenever WordPress's `auth` salt changes (a credential rotation, not a routine release event) and is rejected outright if replayed on a different site (`blog_id` mismatch), including across a multisite network sharing salts.

What *is* a manual rollout step: this change replaces the AJAX wire shape (`data-elemacy-loop-settings`/`settings`+`paged` → `data-elemacy-loop-request`+`request`). A full-page cache or CDN still serving pre-upgrade HTML will embed the *old* markup shape, which this release's controller no longer recognizes at all — `PublicLoopRequest::from_json()` treats a request with no `request` field as legacy and returns `refresh_required` immediately (verified by the now-green task-1.1 baseline, task 1.7 above). That is the correct, safe behavior — no fallback query ever runs — but visitors on stale cached pages will see the pagination area's "refresh the page" notice (task 1.9) until they reload or the cache expires. Purging supported page caches as part of deploying this release (rather than waiting out each cache's natural TTL) is recommended to avoid that transitional UX, exactly as design.md D1 anticipates; this repository defines no page-cache-purge integration of its own for the pagination endpoint specifically (`core/cache-and-schema-lifecycle`'s own invalidation hooks are phase 11's plugin-internal candidate/resolved-result caches, a different concern from an external page cache).

## Task 3.7 — modal stack: opening order, Escape, focus trap, shared scroll lock

**New** `ModalStack` (an IIFE-scoped module inside `engine.js`, not a separate file — no other consumer needs it yet): `push(id)` returns a strictly-increasing order number (not stack position — a popup that closes and reopens must always outrank every still-open modal, including one that opened after it originally did but before it reopened; stack position alone can repeat a value after removals) used to compute each modal's effective z-index (`authored z_index + order`), guaranteeing correct visual stacking by *opening* order even when two modals share the identical authored `z_index` (the fixtures' default, 9999). `remove(id)` is out-of-order safe. The shared scroll lock is reference-counted by which modals actually requested `prevent_body_scroll` (not by call count): the original inline `overflow` is saved once, when the first locker acquires it, and restored once, when the last currently-open locker releases it — regardless of the order in which locking modals close. ## Task 4.6 — cache invalidation on availability change

**New** `Core/Cache/PageCachePurger.php` (Free): `purge_all()` — detects and calls whichever of WordPress's own object cache, WP Rocket, W3 Total Cache, WP Super Cache, LiteSpeed Cache, SiteGround Optimizer, or WP Engine's cache is actually present (each check is `function_exists`/`method_exists`/`class_exists`, a no-op when that plugin/host is absent), then fires **new** `Hooks::CACHE_PURGE_ACTION` unconditionally so anything else caching rendered output can hook the same signal. `LicenseManager` (Pro) now calls it from `activate()`, `validate()`, and `deactivate()` — but only when the call actually flips `is_active()`, computed before and after each call; an already-active license reactivating, a fail-open revalidation, a valid→invalid transition that grace keeps active, or a deactivation of an already-gated install all correctly purge nothing. This matters because `validate()` runs daily via the existing cron (`LicenseBootstrap::REVALIDATE_HOOK`) — purging on every no-op daily check would defeat the purpose of the cache it's meant to protect.

**Documented limitation** (this section, since design.md does not specify a mechanism for this task and no prior cache-invalidation infrastructure existed anywhere in either plugin to extend): `PageCachePurger` can only purge caches Elemacy can reach directly in-process. It cannot purge an edge/CDN cache (Cloudflare, etc.) or any page-cache plugin not in its detection list — those remain bound by their own TTL until their next natural expiry or a manual purge. Separately, the 14-day grace window's *natural* expiry (no server call, no admin action — just elapsed time making `is_active()`'s own time comparison flip) is not a discrete event this mechanism can observe: `is_active()` is a pure computed read with no corresponding "grace just expired" callback, so a page cached while still inside the grace window may continue serving stale (Pro-active) content until whatever next event does trigger a purge (the next `validate()` call that also receives an actual invalid response from the server, an explicit deactivate, or the external cache's own TTL) or a fresh admin action. Building a dedicated scheduled check exactly at grace expiry was judged out of scope for "connect availability changes to cache invalidation" — it would be new time-based infrastructure, not a connection of an existing one.

## Task 6.1 — `Core/Container`: explicit contract bindings and shared/fresh lifetimes

## Task 8.8 — `AcfRepeaterQuery::get_items()`: no longer materializes a row it will immediately discard

**The avoidable cost, precisely identified**: `get_items()` walked ACF's `have_rows()`/`the_row()` cursor across *every* row in the field, constructing a new `AcfRepeaterRowLoopItem` object for each one, then called `array_slice()` to keep only the requested page and discard the rest. The page boundary (`$offset`/`$number`) depends only on the saved settings — `rows_number`, `rows_offset`, the current page — never on how many rows exist, so it can be computed *before* the walk. **Fixed**: the walk now still visits every row (still required to learn `$total_items` for pagination, and to leave the native ACF cursor exactly where `AcfRepeaterRowLoopItem::enter()`'s own forward-walk expects it), but only constructs a `AcfRepeaterRowLoopItem` for a row actually inside `[$offset, $offset + $number)` — every other row costs one integer increment, not an object allocation. Behavior is otherwise identical: same `$total_items`, same `$max_num_pages` formula, same page contents in the same order.

**What is *not* fixed, and cannot be, without ACF supporting bounded reads (design.md D8's own explicit acknowledgment)**: `have_rows($field, $post_id)`'s first call always loads the field's *entire* raw value into memory via ACF's own internals (confirmed by tracing `have_rows()`'s source in task 8.3) — there is no ACF API to read only rows 40–50 of a 5,000-row field. `get_field()` alone (no row walking, no LoopItem construction at all) already carries this same cost; it is the floor no implementation, old or new, can go below.

**Measured, both algorithms in separate processes** (`memory_get_peak_usage()` is monotonic per-process, so a fair comparison needs process isolation, not two calls in one script) — **new** standalone `tests/performance/acf-repeater-query.php --mode={field-only,old,new} --rows=N --page-size=N`, `old` being the pre-fix algorithm reimplemented inline for a like-for-like comparison against the real, current `get_items()`. Fixture: one real ACF repeater field, 5,000 rows (a scale well beyond any observed real-world use, deliberately chosen to make a per-row saving visible at all), requesting a 10-row page:

| Mode | Elapsed | Peak memory (OS-allocated blocks) | Peak memory (PHP's own precise accounting) |
| --- | --- | --- | --- |
| `field-only` (`get_field()` alone) | 70.4ms | 68.50 MiB | 66.62 MiB |
| `old` (materialize all 5,000, then slice) | 84.6–92.4ms (two runs) | 66.50 MiB | 64.52 MiB |
| `new` (materialize only the 10 in range) | 73.8–81.7ms (two runs) | 66.50 MiB | 63.70 MiB |

**Reading these honestly**: the **OS-allocated-block figure is identical between `old` and `new`** — at this scale, ACF's own whole-field load already dominates memory so completely that ~4,990 avoided small object allocations don't cross into a new memory-manager block. **PHP's own precise accounting does show a real, reproducible difference**: `old` minus `new` is consistently ~854KB (67,650,848 → 66,796,912 bytes) across repeated runs — genuine, but a small fraction (~1.3%) of the ~64–68MB the field's own data already occupies. **Elapsed time shows the clearer, more consistently reproducible improvement**: `new` was faster than `old` by 10.7–10.8ms in both paired runs (a ~12–13% reduction) — the CPU cost of ~4,990 avoided object constructions plus a smaller `array_slice()`-free path, independent of whether it moves a coarse memory metric. (`field-only`'s own numbers are not a strictly comparable baseline: it calls `get_field()` directly rather than `have_rows()`/`the_row()`, a different internal ACF code path with its own formatting/filtering, so its precise-memory figure landing *above* both `old` and `new` reflects that difference, not a contradiction — it is included to show the same order of magnitude, not for a byte-for-byte subtraction.)

**Conclusion recorded here, not glossed over**: this task's fix removes a real, measurable, reproducible cost (time consistently, memory precisely) without touching the dominant, unavoidable ACF whole-field-load cost, which no plugin-level change can reduce. The benefit scales with row count and inversely with requested page size — larger fields and smaller pages requested see proportionally more rows avoided.

## Task 10.2 — Closing a real discriminator-override hole in rule/trigger client config

**A genuine, exploitable bug, not a hypothetical**: `BaseRule`/`BaseTrigger::to_js_config()` built the client-facing config as `array_merge(['type' => $this->get_name()], $dto->params)` — `array_merge()`'s "later array wins" semantics meant a stored `params.type` value would silently override the real registered type in the object handed to the browser's popup engine. Every shipped concrete Rule/Trigger (`FrequencyCap`, `PageViews`, etc.) already avoids this by hand-building an explicit whitelist return value, so the hole was reachable only through the two base classes' own default implementation (`MockRule`/`MockTrigger`, and — critically — any third-party extension that does not override `to_js_config()`, which the public `RuleInterface`/`TriggerInterface` contract explicitly allows). Fixed by reversing the merge order (params first, authoritative type last) so the registered type always wins regardless of stored content; found and fixed the identical pattern in `PopupConfigResource`'s own unregistered-type fallback branch at the same time.

**New** shared `Modules/Popups/Support/RuleTriggerParams.php`: rejects a `params` payload containing the `type`/`id` discriminator keys, or a value shaped deeper than a scalar or flat list of scalars (every currently registered `get_config_schema()` across both plugins only ever declares one of those two shapes, confirmed by inspection before relying on it). Wired into `RuleDTO`/`TriggerDTO::collection_or_fail()` — explicitly documented as the write boundary, distinct from `collection()` used for reads, so a pre-existing malformed stored value can never become un-loadable — and, at the request boundary, into `CreatePopupRequest`/`UpdatePopupRequest::clean()`.

## Task 11.4 — Generation-guarded rebuilds, a bounded expiring lock, and narrowed metadata loading

**Generation + lock**: added a small autoloaded `elemacy_library_index_generation` counter, bumped on every `invalidate()`. A scheduled rebuild (whether from `invalidate()`'s own `shutdown` callback or `get_index()`'s cache-miss path) captures the generation it started under and re-checks it — once before, once after, the actual candidate query — discarding its own result rather than persisting if a newer write landed in the meantime, so a rebuild delayed behind a slow query can never overwrite a faster, newer one. A WordPress transient (`elemacy_library_index_rebuild_lock`, 30s TTL) reduces redundant concurrent rebuild queries; correctness against a stale overwrite is the generation check, not the lock, so losing the race to acquire it is always safe to skip — and per design.md D11's explicit "do not block a public request indefinitely," `get_index()`'s own cache-miss path always builds and returns a correct, freshly-computed index for its own caller immediately, whether or not it wins the lock to *persist* that result for the next request.

Replaced with one targeted `$wpdb->get_results()` selecting only those two meta keys for the candidate id set.

## Task 11.5 — Separating schema version from plugin release version

**The exact conflation design.md D11 names**: `Core/Elemacy.php::handle_version_update()` stamped `OptionKeys::DB_VERSION` with `ELEMACY_VERSION` (the plugin's own release string) *and* passed that same value as `Migrator::run()`'s upgrade target — one option doing double duty as both "which release did this site last see" and "which data migrations have applied." Two concrete consequences, both matching the task's own verification list: a release with zero new migrations still advanced the marker (masking nothing today only because `migrations()` is empty — the moment a real migration is added and a later hotfix release ships with no migration of its own, that hotfix would still bump the marker past the migration's own version key, and if a subsequent migration were ever added between a maintenance release and the intended next feature release, sites that already went through the maintenance release could skip a migration they never actually ran) and, more immediately, an unconditional `update_option(DB_VERSION, ELEMACY_VERSION)` at the end of `handle_version_update()` ran even on a **downgrade**, lowering the stored marker to the older code's own version and making already-completed migrations look pending again on a later re-upgrade.

**Fix**: `DB_VERSION` now only tracks the release for diagnostics and `Hooks::VERSION_UPDATED_ACTION`'s own fired args — never consulted by anything migration-related. **New** `OptionKeys::SCHEMA_VERSION`, owned entirely by `Migrator` (nothing outside it ever writes this option): `Migrator::run()` stamps it (not `DB_VERSION`) after each completed step, exactly as before, and **new** `Migrator::sync(bool $is_fresh_install)` owns the seeding decision Elemacy's bootstrap previously made inline — moved there rather than kept on `Elemacy` itself so it is unit-testable without instantiating the full bootstrap singleton (whose constructor has real hook-registration side effects). ## Task 11.7 — Bounded, resumable multisite network activation

**The unbounded operation design.md D14 names**: `Elemacy::activation_actions()`'s network-activation branch previously called `get_sites(['number' => 0])` (fetch every site, no limit) and then seeded each one synchronously in a single `foreach`, inside the one activation request — on a network of hundreds or thousands of sites, this can exceed a request's execution-time limit outright, silently leaving the tail of the network unseeded with no record that anything was left to finish.

**New** `Core/Multisite/SiteBatchIterator.php`: `process_batch(callable $callback, int $offset, int $limit): array{processed:int, has_more:bool}`. Fetches `$limit + 1` site IDs at `$offset` (one extra reveals whether more remain without a second, separate `COUNT` query), switches into each of the first `$limit` via `switch_to_blog()`, and always restores the prior blog via a `finally` around the callback — including when the callback throws, so one failing site cannot leave a later batch, or a later request, stuck on the wrong blog. Deliberately self-contained (no dependency on any other class in either plugin, per design.md D14) so Free's and Pro's own future uninstall routines (tasks 14.4/14.5) can each keep an independent copy that keeps working even if the sibling plugin is already gone.

**Bounded activation + resumption, mirroring `Migrator::sync()`'s own pattern from 11.5/11.6**: network activation now seeds a network option (`elemacy_network_seed_offset`, via `get_site_option()`/`update_site_option()` — a network-wide job, not a per-blog one) at `0` and runs exactly one bounded batch of `NETWORK_SEED_BATCH_SIZE` (100) sites via `SiteBatchIterator`. ## Task 12.1/12.2 — A versioned, readiness-gated admin bridge; Pro defers until it is confirmed compatible
